# ERP Module Relationships

## Architecture traced

Mobile screens call a shared Axios client in `mobile/src/api/client.ts`, which reads `API_CONFIG.BASE_URL` and obtains a bearer token from the storage service. Express mounts routers from `backend/src/routes/index.ts` below `/api/v1`. Controllers call service classes; services issue parameterized MySQL queries using the shared `mysql2` pool. The schema is `database/schema.sql` and currently contains 81 `CREATE TABLE` statements and 155 foreign-key declarations.

This is a source-level trace. No end-to-end mobile-to-MySQL workflow was executed against an isolated database.

## Concrete integration risks

- Student creation now requires relationship IDs and validates the user and academic path against the selected college. User creation and student profile creation are still not one atomic workflow.
- Reviewed dashboard and module read paths now propagate database failures instead of returning empty/sample rows. Coverage is incomplete across all controller and service methods. Audit insert failures reach server logs, but the audit writer remains best-effort and is not transactionally coupled to all mutations.
- Student list/detail now require `students.view` and are filtered by college; create requires `students.create`, a linked student user, and matching college/program/course/year/semester relationships. This does not yet prove all foreign-key paths or individual student ownership requirements.
- Faculty list/detail now require `faculty.view` and filter to the authenticated user's college.
- Certificate request reads are limited to the student's own requests or, for staff, require `certificates.manage` and apply the authenticated college scope. Staff status updates use the same college relationship constraint.
- Dashboard and scoped complaint, exam, leave, notice, library, placement-drive/application, assignment, and timetable paths reject missing college scope. Student, faculty, HOD, and parent dashboards now scope linked records and notices to their college. Timetable reads derive student/faculty scope from identity and verify parent-student links; writes validate academic year, semester, division, subject, faculty assignment, classroom, and optional batch within the college. Assignment reads/mutations validate college and role ownership, and submissions map to the authenticated student profile. Super Admin academic/settings paths require an explicitly selected college and validate academic relationships; a complete route-by-route tenant integration matrix remains outstanding.
- Protected requests check current account status and soft-deletion state and refresh college, role, and permission claims from the database. An unavailable status/claim lookup denies access with HTTP 503.
- College Admin account status lookup and update require target users to match the caller's college and block Super Admin targets. Complaint status updates are mounted behind `complaints.manage`, validate same-college assignees, and constrain the target complaint to the selected college; the mobile app still lacks a manager-resolution screen.
- Faculty class roster and attendance submission derive identity from the token and verify division, timetable, batch, and student membership before writing attendance.
- Placement applications resolve the authenticated `users.id` to an active `students.id` in the same college before insert; drive and application reads/status changes carry college scope. Company/internship records are global in the current schema because those tables have no `college_id`, so tenant isolation cannot be enforced for those catalog operations without a schema/product decision.
- Super Admin academic/settings reads and writes now require an explicitly selected college and academic relationships are checked within that college. Super Admin mutation audit writes now receive request actor/IP context; other module mutations do not consistently emit audit events, and storage encryption/atomic persistence remain unverified.
- Student and parent dashboard semester names now join through `students.academic_year_id` to `academic_years.college_id`; the prior SQL referenced a nonexistent `semesters.college_id`. Librarian issue totals and institutional department student counts now require matching college IDs. Mocked assertions cover these clauses, but the repository has no disposable MySQL fixture to prove execution.
- The schema file disables FK checks while dropping and rebuilding tables. It is unsuitable as an incremental migration and must not be applied to a data-bearing database.
- The repository has no migration tool or migration history, so the current schema and a running database cannot be proven synchronized from source alone.
